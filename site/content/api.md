# Blip API reference

Generated by `blip doc lib/std.blip`; do not edit.

## identity

```blip
(identity x)
```

lib/std.blip -- the blip standard library, in blip.

Loaded by `blip run` and by the REPL before your program, so a program does not
have to say `(require "std.blip")` for names everybody assumes exist. That is
the same rule every language with a prelude follows, and it is what lets the
examples in examples/ read the way they do: `(parse-in "key: value")` is a
call, not a definition the reader has to scroll past.

Everything here is ordinary blip. There is no special form in this file, which
is the point: if the standard library needs a new feature, the feature is
missing rather than the library being special.

The Result-returning names are the convention the language settles on: a
function that can fail for an expected reason returns `(ok v)` or `(err 'why)`,
and `use` binds the values without a staircase. A function that fails for an
impossible reason calls `raise`.
---------------------------------------------------------------- results

## err-message

```blip
(err-message e)
```

err-message reads the message out of an `(err msg)` value. `raise` builds one
and `try`'s #:catch matches against it, so this is how a handler reads what
went wrong.

## map-result

```blip
(map-result r f)
```

The Result combinators are ordinary blip. The machine keeps only
construction and observation (`ok`, `err`, `ok?`, `err?`, `ok-value`,
`err-value`); everything that maps over a Result is defined here, so both
engines run the same code. A non-Result passes through `map-result` and
`flatten-result` untouched, exactly as the machine builtins did: only an
`(ok _)` is mapped, only an `(err _)` is an error.
map-result turns (ok v) into (ok (f v)) and passes anything else through
untouched -- including an (err _) from f itself, which is returned as is
rather than wrapped.

## unwrap-or

```blip
(unwrap-or r fallback)
```

unwrap-or takes the value out, or the fallback when there is none. The
parameter is not named `default`: that is a reserved word in JavaScript,
and the emitter compiles this file too.

## flatten-result

```blip
(flatten-result r)
```

flatten-result peels one level: (ok (ok 1)) is (ok 1), and so is
(ok (err 'inner))'s inner. Anything else is already flat.

## all-results

```blip
(all-results . rs)
```

all-results collects every value into a vector, or returns the first
error. The walk is quadratic in the number of results -- vector-append
copies -- which is the price of building a vector without `apply`, and
`apply` does not splice under node the way the machine splices.

## all-results-from

```blip
(all-results-from rs acc)
```

all-results-from is the carrying half of all-results, kept under its own
name so the name a program writes stays the name that reads well.

## lazy-unwrap

```blip
(lazy-unwrap r thunk)
```

lazy-unwrap runs the thunk only on err: the default is computed nowhere
else, because in a Lisp every argument is evaluated eagerly.

## lazy-map-result

```blip
(lazy-map-result r f)
```

lazy-map-result maps over an (ok _) and passes an (err _) straight
through, like map-result. The name states the intent at the call site.

## pad

```blip
(pad s width)
```

---------------------------------------------------------------- strings
Padding is spaces, to a width, never truncating: a value longer than the
width is already aligned. `pad` pads on the right (columns read left to
right); `pad-left` pads on the left (numbers line up).
pad pads on the right with spaces.

## pad-left

```blip
(pad-left s width)
```

pad-left pads on the left with spaces.

## as-list

```blip
(as-list xs)
```

---------------------------------------------------------------- tables
Paths, merges, subsets, and order. `get` is total (nil on a miss) and
`table-keys` lists every key in insertion order, so the rest is ordinary
blip: `get-in` walks a path of keys, `merge` overlays left to right with
later keys winning, `select-keys` keeps a subset, `vals` reads every
value in insertion order, and `sort-table` rebuilds a table sorted.
Paths and key sets read naturally as vectors, so a small `as-list`
normalizes them once instead of every caller checking twice.
as-list turns a vector into a list of its elements; lists pass through.

## vals

## sort-table

```blip
(sort-table t)
```

sort-table rebuilds a table with its keys sorted: the explicit sort for
callers that want alphabetical. Folding the sorted keys in order is what
makes the new table's insertion order the sorted one.

## parse-line


---------------------------------------------------------------- fs
Promoted from programs/config.blip, which keeps its demo: key: value

## read-config

```blip

```

read-config folds a key: value file into a table. A read failure stops

## tmp-dir

```blip
(tmp-dir )
```

tmp-dir answers a scratch directory: TEMP, then TMP (Windows
conventions), else /tmp. An unset variable is nil, which is truthy
here, so unset-ness is tested with `nil?`, never `or`.

## elapsed

```blip

```

---------------------------------------------------------------- time
`now` is unix seconds as an integer. The clock is not ordinary blip --

## json-code

```blip
(json-code text pos)
```

---------------------------------------------------------------- json
Promoted from programs/json.blip, which keeps its driver and its
asserts: the file that proved the code is the file that still runs it.
Values: objects become tables with string keys, arrays become vectors,

## zip

```blip
(zip a b)
```

---------------------------------------------------------------- seq
Zipping, indexing, and chunking. These take lists and answer lists;
the polymorphic builtins (`map`, `filter`) already serve every
container, and these fill the missing shapes, not a second copy of
them. A `keep` is deliberately absent: v2 removed it as a duplicate
of `filter`, and `(def keep filter)` in your own file is the alias
recipe -- the core and the std carry one spelling each.
zip stops at the shorter input: no padding, no silent miss.

## peg-char

```blip
(peg-char input pos)
```

---------------------------------------------------------------- peg
PEGs as data (roadmap B5): the grammar is an ordinary table, so `match`
covers structure and PEG covers text, and neither knows about the other.
No match, no macros anywhere in this section: the gate demands a grammar
fixture independent of match, so the dispatcher is `cond` over the head
keyword and every combinator is a function. A rule is a vector:
[:lit "key"]      literal text at the position
[:any]            any single character (fails at end of input)
[:one-of "ae"]    one character from the set
[:range "a" "z"]  one character in the range, inclusive
[:seq r ...]      each rule in order; the value is the list of values
[:choice r ...]   the first rule that matches (ordered, like PEG)
[:star r]         zero or more; the value is the list of values
[:plus r]         one or more
[:opt r]          the value, or nil when it misses (position kept)
[:not r]          succeeds empty when r fails, fails when r matches
[:look r]         succeeds empty when r matches (lookahead)
[:cap r]         the matched TEXT (a substring, not the value)
[:ref :name]     another rule in the same grammar (recursion)
Left recursion does not terminate -- that is the PEG bargain, not a bug --
so grammars loop with star and plus. A star over a rule that matches
empty stops after one empty step rather than spinning: progress is what
keeps it honest.
peg-char reads the character at pos, or "" past the end.

## array-append!

---------------------------------------------------------------- arrays
array-append! pushes every element of src onto the end of dst, in order, and

---------------------------------------------------------------- debug

## *tests*

---------------------------------------------------------------- test
deftest/is/run-tests: the test framework is ordinary blip, not macros.
Two engine facts force that shape, and both are pinned in tests/unit.v:
the machine never auto-expands a bare macro call (only `macex` and the
emitter pre-pass expand), so a `defmacro` deftest would die with
`unbound identifier` under `run` and a bare `is` would evaluate its
argument and return the expansion as a value -- a test that cannot fail.
And `assert` renders its message from SOURCE, so a function wrapping it
would report the wrapper's parameter name; `raise`/`error` evaluate, so
the caller's message arrives intact on both engines.
The call shape pays for honesty: `(deftest 'name (fn [] ...))` quotes the
name and wraps the body, because no macro is there to leave them
unevaluated. `run-tests` answers the count of tests run; a failure raises
past it, so a count in hand means everything passed. `table-keys` is
insertion order, so the run order is registration order.
*tests* maps names to thunks. A global, rebound by registration, which is
what `set!` is for.

## is

```blip
(is test . rest)
```

is checks one claim: nil on success, a raise carrying the message on
failure. The message is explicit, defaulting to a generic one, because a
function cannot capture its argument's source the way a macro could --
and a macro could not run.

## is-msg

```blip

```

is-msg is the defaulting half of `is`, named separately the way
`enumerate-from` carries for `enumerate`: one name that decides, one that
defaults. It is also directly testable, being pure.

## run-tests

```blip

```

run-tests runs every registered test in key order, answering the count.

## run-each

```blip
(run-each ks)
```

run-each is the index-free walk over the key list: call, count, recurse.
A test that raises never returns, so the count only completes when all
pass -- there is no separate tally of failures to consult.
